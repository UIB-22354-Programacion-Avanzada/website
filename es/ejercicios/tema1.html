Ejercicios — Tema 1: POO, Principios SOLID y Diseño

Cómo trabajar estos ejercicios

Los 28 ejercicios de esta página acompañan al contenido del Tema 1 y se numeran 1.X.k, donde X es el subapartado del tema al que corresponden. Cada enunciado indica con precisión qué clase escribir, en qué paquete, con qué firma y qué comportamiento debe tener: lo que se te pide es exactamente eso, ni más ni menos.

No empiezas desde una carpeta vacía. En la organización del curso tienes el repositorio t1-ejercicios, una plantilla con la misma estructura que t1-ejemplos que contiene:

  • un esqueleto de cada clase que se pide, con su firma y un comentario // TODO en el cuerpo;
  • una copia del código del monitor (paquete es.uib.prgava.tema1.monitor) que puedes usar y, cuando el enunciado lo pida, modificar libremente;
  • las pruebas que comprueban tu solución, en src/test/java, salvo en los ejercicios de la sección 1.4, donde las pruebas son precisamente lo que tienes que escribir.

El esqueleto compila desde el primer momento, pero casi todas las pruebas fallan hasta que completas el código. El flujo de trabajo es el habitual: crea tu copia con Use this template, abre un Codespace, ejecuta mvn test, y ve resolviendo ejercicios hasta que la construcción pase en verde. Las soluciones no se publican; en clase se comentan las que más dudas generen.

Sobre los paquetes: las clases que implementan una interfaz del monitor (FallosEnVentana, NotificadorFichero, SondaConRegistro, ServicioPing) viven en es.uib.prgava.tema1.monitor, junto a sus compañeras; todas las demás, en es.uib.prgava.tema1.ejercicios. El esqueleto ya trae cada fichero en su sitio, así que basta con que respetes el que te encuentres.

Dos ejercicios de la sección 1.4 consisten en escribir las pruebas de clases que ya has construido antes (1.4.1 las de FallosEnVentana, 1.4.2 las de DireccionIpv4). Para que no te quedes sin comprobación mientras tanto, la plantilla incluye un puñado de pruebas mínimas de esas dos clases, en FallosEnVentanaBasicoTest y DireccionIpv4BasicoTest. No las repitas en las tuyas.

Estos ejercicios son la base de los Talleres y del Examen Parcial. Resolverlos leyendo la solución de otra persona no sirve de nada: lo que se evalúa es que sepas justificar cada decisión de diseño, no que el código funcione.

1.1. Conceptos fundamentales de la POO en Java

Ejercicios sobre 1.1 del tema: clases y objetos, encapsulación e invariantes, herencia, polimorfismo, jerarquías selladas y excepciones.

Nota1.1.1 Registro DireccionIpv4

Escribe un record DireccionIpv4(int primero, int segundo, int tercero, int cuarto) que represente una dirección IPv4 como cuatro octetos.

  1. Constructor compacto. Cada octeto debe estar entre 0 y 255. Si alguno no lo está, lanza IllegalArgumentException con el mensaje "Octeto fuera de rango: " + valor (el valor inválido, no la dirección entera).
  2. Fábrica estática public static DireccionIpv4 desde(String texto). Acepta cuatro números separados por puntos. Si no hay exactamente cuatro partes, o alguna no es un entero, lanza IllegalArgumentException con un mensaje que incluya el texto recibido.
  3. toString() redefinido para devolver la forma habitual 192.168.1.1 (el toString generado por el record no sirve aquí).
  4. public boolean esPrivada(): devuelve true para los rangos privados 10.x.x.x, 172.16.x.x–172.31.x.x y 192.168.x.x.

No escribas equals ni hashCode: parte del ejercicio es entender por qué no hacen falta.

TipEjemplo de uso 
var ip = DireccionIpv4.desde("192.168.1.1");
System.out.println(ip);                                  // 192.168.1.1
System.out.println(ip.esPrivada());                      // true
System.out.println(ip.equals(new DireccionIpv4(192, 168, 1, 1)));   // true
DireccionIpv4.desde("192.168.1.300");                    // IllegalArgumentException
Nota1.1.2 Clase Servidor

Escribe una clase Servidor tradicional (no un record) que modele un servidor con nombre, dirección y puerto. El objetivo es practicar la encapsulación con todas sus piezas.

  1. Atributos privados: nombre (String), direccion (DireccionIpv4), puerto (int) y enServicio (boolean).
  2. Un atributo de clase private static int servidoresCreados, que cuenta cuántos objetos Servidor se han construido, con su método de acceso public static int getServidoresCreados().
  3. Constructor Servidor(String nombre, DireccionIpv4 direccion, int puerto) que rechaza nombres nulos o en blanco y direcciones nulas (Objects.requireNonNull o IllegalArgumentException, según proceda), valida que el puerto esté entre 1 y 65 535, deja el servidor fuera de servicio e incrementa el contador.
  4. Constructor sobrecargado Servidor(String nombre, DireccionIpv4 direccion) que use el puerto 443 delegando en el anterior con this(...). No repitas la validación.
  5. Comportamiento: arrancar() y parar(), que cambian enServicio.
  6. Métodos de acceso getNombre(), getDireccion(), getPuerto(), isEnServicio().
  7. equals y hashCode basados solo en dirección y puerto (dos servidores con el mismo nombre en máquinas distintas no son el mismo servidor), y un toString() legible.

No escribas setDireccion ni setPuerto. Añade un comentario de dos líneas explicando qué invariante te permite mantener esa decisión.

TipEjemplo de uso 
var web = new Servidor("web", DireccionIpv4.desde("10.0.0.1"), 80);
var otro = new Servidor("web-replica", DireccionIpv4.desde("10.0.0.1"), 80);
web.arrancar();
System.out.println(web.isEnServicio());                  // true
System.out.println(web.equals(otro));                    // true: misma dirección y puerto
System.out.println(Servidor.getServidoresCreados());     // 2

Nota1.1.6 Clase LectorUmbrales y excepción propia

Cada servicio puede tener su propio umbral de latencia. Escribe el lector de ese fichero de configuración, practicando try-with-resources, excepciones propias y encadenamiento de causas.

  1. public class UmbralInvalidoException extends RuntimeException con un campo linea (int), dos constructores (con y sin causa) y un método de acceso linea(). El mensaje debe empezar por "Línea N: ".
  2. public final class LectorUmbrales con public static Map<String, Duration> leer(Path fichero):
    • lee el fichero con Files.lines dentro de un try-with-resources;
    • ignora las líneas vacías y las que empiezan por #;
    • cada línea válida tiene la forma nombreServicio=milisegundos;
    • una línea sin =, con el nombre vacío, con un número no entero o con un valor negativo o cero produce UmbralInvalidoException indicando el número de línea (empezando en 1) y, cuando exista, encadenando la causa original;
    • una clave repetida también es un error;
    • devuelve un mapa inmutable.
  3. Escribe un main que lea un fichero con un error deliberado, deje escapar la excepción y copie en un comentario el stack trace resultante, señalando la línea de tu código y la línea de la causa.
TipFichero de ejemplo (umbrales.txt)

1.2. Principios SOLID y patrones de diseño canónicos

Ejercicios sobre 1.2 del tema. En varios de ellos la plantilla incluye una versión mal diseñada que debes refactorizar: no la reescribas desde cero, transfórmala paso a paso comprobando que el comportamiento observable no cambia.

Nota1.2.1 Refactorizar RegistroSensores (principio S)

La plantilla incluye RegistroSensores, una clase que almacena lecturas de sensores, calcula estadísticas sobre ellas y además las exporta a un fichero CSV.

  1. Enumera en un comentario cuántas razones para cambiar tiene la clase y quién pediría cada uno de esos cambios.
  2. Sepárala en dos clases con una única responsabilidad cada una:
    • EstadisticasSensor, que solo calcula (media, máximo, mínimo, número de lecturas) y no toca el sistema de ficheros;
    • ExportadorCsv, con un único método escribir(Path destino, List<String> filas), que solo escribe lo que recibe y no conoce la lógica de cálculo.
    EstadisticasSensor ofrece además List<String> comoFilas(), que prepara las filas del CSV empezando por la cabecera metrica;valor: así el exportador sigue sin saber nada de sensores.
  3. Escribe un main que las use juntas y produzca exactamente la misma salida que la clase original.
  4. Comprueba lo que has ganado: escribe una aserción sobre la media sin crear ningún fichero.
Nota1.2.2 Clase FallosEnVentana (principio O + Strategy)

Añade una política de alerta nueva sin modificar Monitor ni la interfaz PoliticaDeAlerta.

Escribe public final class FallosEnVentana implements PoliticaDeAlerta:

  1. Constructor FallosEnVentana(int minimoFallos, int tamanoVentana). Valida que 1 ≤ minimoFallos ≤ tamanoVentana; en otro caso, IllegalArgumentException.
  2. debeAlertar(List<Resultado> historial) devuelve true si entre las últimas tamanoVentana comprobaciones hay al menos minimoFallos fallos. Si el historial tiene menos elementos que la ventana, considera los que haya. A diferencia de FallosConsecutivos, los fallos no tienen que ser seguidos.
  3. toString() descriptivo, por ejemplo "2 fallos en las últimas 5 comprobaciones".
  4. En Principal, sustituye la política actual por new FallosEnVentana(2, 5).o(new LatenciaExcesiva(Duration.ofMillis(500), 5)) y comprueba que Monitor no ha necesitado ni una línea de cambio.
TipCasos que debe cumplir 
var politica = new FallosEnVentana(2, 5);
politica.debeAlertar(List.of());                              // false
politica.debeAlertar(List.of(FALLO, OK, OK, OK, FALLO));      // true  (2 fallos en 5)
politica.debeAlertar(List.of(FALLO, OK, OK, OK, OK, OK));     // false (el fallo quedó fuera)

Nota1.2.9 ConfiguracionInforme con Builder, y Optional como retorno

1.3. Genericidad en Java y Stream API

Ejercicios sobre 1.3 del tema. En los que usan la Stream API, no se admiten bucles for ni while salvo que el enunciado lo autorice expresamente.

Nota1.3.1 Clase genérica Historial<T>

Escribe public final class Historial<T>, una colección que conserva como máximo los últimos n elementos añadidos.

  1. Constructor Historial(int capacidad) que rechace capacidades menores que 1.
  2. public void anadir(T elemento): si el historial está lleno, descarta el más antiguo antes de añadir. Usa un ArrayDeque<T> como almacén interno.
  3. public List<T> ultimos(int n): devuelve como máximo los n elementos más recientes, ordenados del más reciente al más antiguo, en una lista inmutable. Si n supera el número de elementos disponibles, devuelve todos los que haya.
  4. public int tamano(), public boolean vacio(), public boolean lleno().
  5. En un comentario, explica por qué ultimos devuelve List.copyOf(...) y qué podría ocurrir si devolviera directamente la colección interna.
TipEjemplo de uso 
var historial = new Historial<String>(3);
historial.anadir("a"); historial.anadir("b");
historial.anadir("c"); historial.anadir("d");
System.out.println(historial.ultimos(2));    // [d, c]
System.out.println(historial.tamano());      // 3: "a" se descartó
Nota1.3.2 Métodos genéricos con cotas en UtilidadesEjercicio

Escribe una clase de utilidades, no instanciable (constructor privado), con tres métodos genéricos estáticos:

  1. public static <T extends Comparable<? super T>> Optional<T> minimo(Collection<? extends T> elementos), que devuelve el menor elemento, o vacío si la colección lo está.
  2. public static <T> long contarSi(Collection<? extends T> elementos, Predicate<? super T> criterio).
  3. public static <T extends Comparable<? super T>> List<T> ordenadoDescendente(Collection<? extends T> elementos), que devuelve una lista nueva e inmutable.
